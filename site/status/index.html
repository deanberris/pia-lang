    Status and roadmap¶

    Pia is an experimental language under active development. The compiler proves and compiles a growing part of the language, and the rest is designed but not built. The feature index lists every built feature with a proved example, and the standard library every module written with them. Nothing is stable yet: syntax, flags and the compiled ABI can all change before a 0.1 release.

    What works today¶

    Area Status
    Parser The whole grammar in grammar.md, including the parts the later stages do not handle yet
    Types Bounded integers, range types int{lo..hi}, bool, f32 and f64, fixed arrays [T; n], slices [T], records, variants, recursive let rec variants, type aliases (let byte = u8) and distinct types (type u32) with derived operators (ADR 0064)
    Code Functions, let rec, let ... in, mutable locals and buffers, if, for, while, parameter modifiers, lambdas and function values, error sets with ? and handle, defer
    Overflow @overflow(proof) by default, plus wrap, saturate and trap, and saturating operators
    Contracts requires, ensures, assert, assume (only in a file marked @trusted), old, forall and exists, loop invariant and decreases, spec functions and lemmas, the spec-only types int (unbounded) and real, theories (sorts, abstract functions and axioms with triggers) and their models, which prove the axioms and are sealed from clients, where refinements on record fields and record invariants over all fields (type { ... } where p, ADR 0074), consistency checks of trusted theories, --trust-report --why with the axioms and assumes each goal used, theories built by metaprograms, such as the prelude's machine (verifier.md), and solver strategies (@solver) and tactics (@by), metaprograms that write proof steps (verifier.md), --check-vacuity, which fails a goal proved from contradictory hypotheses, and lemmas proved in Lean 4 (= by lean T, piac --emit=lean, receipts from the pia_lean_proof rule, recorded in certificates and --trust-report), over int, bool and records so far (verifier.md, ADR 0061)
    Verification Overflow, nonzero divisors, bounds, preconditions at calls, postconditions and assertions, by intervals and Z3, with counterexamples; nonlinear integer goals by int-blasting (ADR 0066); cost bounds, costs iterations <= e and costs calls <= e (verifier.md, ADR 0062, step 1)
    Metaprograms let meta functions, quotes and splices, hygiene, operators defined in the prelude and by programs, @derive(eq), and @derive(ord, add, scale, bounds) on a distinct type, expansion to a fixed point; tests generated from contracts by Pia.Test.Gen (cases, with boundary values, pairwise rows, and a specification check and an oracle per case, proved where they land; meta.md, ADR 0056, steps 1 and 2 of 9)
    Comments (* *), \ line and (** *) doc comments, kept in the syntax tree for metaprograms and hover; literate .pia.md files
    Modules one module per file with a module header; everything is private unless an interface the module claims lists it; each listed item is checked against the module, with contracts proved, and a listed definition that states no contract takes its interface's (ADR 0077); @abi(c) interfaces keep C names; piac --emit=interface writes canonical .piai artifacts, import M.I finds them on --iface-path and checks callers against their contracts (an overloaded function comes in as its whole overload set, each overload checked against its own definition), modules link through __pia$M$f symbols, and the pia_library and pia_binary Bazel rules build modules separately with strict dependencies (ADR 0039, steps 1 and 2 of 7, and step 3 in part: interfaces show records, variants and generic types, which importers use as M.t with the variants' constructors in scope, and list concepts, generic functions and spec functions, which come with their definitions, and state postconditions of functions that write their parameters, and import M.I as X { a, b }; step 4 in part: values, shown with = or known only by type; step 6 in part: a module proves the instances of its concepts at its own and built-in types once, and importers do not prove them again; qualified quotes and module state follow)
    Certificates every object carries a certificate naming its module, the interfaces it provides and the ones it was proved against, each with its hash, its trusted lowerings, and (format 3) the Pia ABI version and target, piac's version, Z3's and the proof engines used; pia-cert check, run by every pia_library build, refuses an object proved against an interface no object provides or provides differently, and objects for another ABI version or target; piac --version prints the version a certificate records; advisories in security/advisories/ are compiled into pia-cert, which refuses objects proved by a revoked piac or solver unless --accept-advisory=<id>:<module> names them, and --require-released refuses unstamped builds (abi.md, ADR 0073, steps 1 to 4 of 7: a revoked z3 also turns off the proof cache; migrations and the runtime check follow)
    Concurrency and the GPU spread, a parallel loop whose iterations are proved to own the cells they write, run on the CPU by MLIR's async runtime (ADR 0060); @place(gpu) on a spread whose iteration i writes cell i runs it on an Apple GPU through SPIR-V and Metal, with the same proof (placed.pia.md, ADR 0068, step 3), and @place(gpu) on a for runs its spreads as one command buffer, which makes the sediment pull step 2.2 times faster on the GPU than on the CPU (pull_gpu.pia.md); atomic cells (ADR 0052)
    Codegen arm64 macOS and x86_64 Linux through MLIR and LLVM (ADR 0049): object files, assembly and LLVM IR, a C ABI for exported functions, saturating NEON instructions and vectorised loops; lowerings written in Pia, where @lower("mlir") gives a function with a proved Pia body an MLIR form, such as linalg.matmul, compiled on the CPU through convert-linalg-to-loops, trusted for now and listed in --trust-report and the certificate, with --lower=off to compile the body instead, and @lower(gen args) computed by a metaprogram (codegen.md, ADR 0065, steps 1 and 2 of 9), and @lower("memref<$s x $t>", data) on a record type, which a lowering splices as a memref view of its buffer (ADR 0074, step 3a)
    System POSIX for arm64 macOS and x86_64 Linux in Pia.Sys.Posix, generated from each target's headers behind one hand-written interface of contracted rows, with the constants' values hidden so proofs hold on both (ADR 0057); C variadic calls (@variadic(n)) and pointer results read in place (@deref, for errno); files in Pia.Sys.Fs: a @linear file, errors as a decoded errno variant, and open_read, create, read_some, write_all and close, proved once for both targets
    Demo Edge detection: a Pia image pipeline, proved and compiled into a program you can run with bazel run //examples/edges; stream delineation, a literate program with sink filling, D8 directions, flow accumulation and watersheds, run with bazel run //examples/streams; sediment transport, proved to conserve mass, by basin in parallel and in pull form; D8 directions and the picture on the GPU, and the CPU and GPU side by side
    Tools piac, pia-opt, the pia-lsp language server and a VS Code extension, and pia repl, a verified REPL with a JIT, a JSON mode, an MCP server (pia mcp), proved live redefinition of code that background tasks are running, and state with invariants and verified migration

    Known limitations¶

    • Loops need invariants. After a loop, only its invariant is known, so a goal after the loop that depends on what it did needs an invariant that says so.
    • Termination is checked for loops and direct recursion only. A while loop or a recursive call without decreases is a skipped goal, which piac refuses unless --allow-unproved accepts it. Mutual recursion is not checked.
    • Calls inside contracts to functions other than spec functions and pure functions of scalars are unknown values, so a contract cannot rely on what such a function computes.
    • Counterexamples do not show array contents yet, only lengths and scalar values.
    • Function values are partly compiled. Typed lambdas without captures, and top-level functions, can be passed to a parameter of function type, which may carry a contract, and a lambda can be bound by a let and applied (ADR 0044, steps 1 and 2). So can function objects, any record or variant with an apply, which g x calls. Function is a standard concept, and an overload set may mix functions that take values with functions that take functions. Lambdas list their captures, each copied, borrowed or referenced (inout), with loans checked to the lambda's last use (step 3). Untyped lambdas take their parameter types from where they are passed, and a let of an untyped or explicitly generic lambda is generic (step 4). Each call with a function argument is proved and compiled as its own specialisation. Partial application (add 1), functions as results (: u8 -> u8) and moved captures work too (step 7). A let of a function type holds a reference to a top-level function, proved against the arrow's contract once, with calls through it seeing only that contract (ADR 0071, step 1). A mutable reference of scalars can be rebound with <-, and a call through it compiles to an indirect call. Generic lambdas that capture, and functions stored in data, come later.
    • Floats are bit patterns to the prover with exact IEEE order, until ADR 0038's real-valued encoding lands: a goal that needs what + or * computes fails rather than being proved (verifier.md).
    • Not compiled yet: functions stored in data and generic lambdas that capture, dyn, vec<T, k>, refinement types and where on values, nested modules, and the concurrency runtime beyond spread. piac reports these as "not supported yet" at their source location.
    • Two targets, one GPU. Code generation targets arm64 macOS and x86_64 Linux; @place(gpu) runs only on Apple GPUs, through Metal.

    Roadmap¶

    The plan is a sequence of milestones, each a GitHub issue, building towards the flagship demo: stream delineation and sediment transport over a terrain heightmap, proved correct and running across the CPU and GPU (ADR 0016).

    Milestone Scope
    M0 to M7 Bazel build, grammar, parser, MLIR dialects, IRGen, verifier, arm64 codegen, records and the metaprogram engine done
    M8 Modules, explicit interface imports, proof certificates and a link check next
    M9 Generic types, concepts with laws, adapters and call-site deduction generic types and functions, value parameters on types (block u8 4) and functions generic over them, deduced from the arguments and shapes, (s : shape) with [4; 4] or [m; k] (ADR 0074, step 2: literal extents; ? extents come with step 3), overloading, concepts, the definition check, adapters, ranking by constraints and choosing by preconditions done (ADR 0034 complete); generic bodies proved once over their type parameters as well as at each instance (ADR 0043, step 1 of 5); ADR 0035: type-level metaprograms in types and where predicates, their totality check, and soft failure with --explain-overloads done (ADR 0035 complete)
    M10 Vectorisation driven by proved facts, and vec<T, k>
    M11 Floats: strict IEEE, and three ways to allow reassociation f32 and f64: literals, + - * /, negation, IEEE comparisons, conversions to and from integers and between widths, to_bits/from_bits, buffers and record fields of floats, C calls, strict codegen (no FMA contraction, subnormals kept); proofs see floats as bit patterns, with exact IEEE order and uninterpreted arithmetic until ADR 0038's encoding
    M12 Concurrency: spread, collectives, and compile-time checks that collectives match spread v0 done, on the CPU and, with @place(gpu), on the GPU; collectives next
    M13 PNG and GIF decoding and encoding, written in Pia GIF decoding and animated encoding, deflate and zlib done (ADR 0054); PNG next
    M14 The stream delineation demo delineation done, sediment transport done, its GIF animation written by Pia's own encoder
    0.1.0 The first release: a small LLM, llama2.c's TinyStories, ported to Pia, proved, and running on Apple silicon with its matrix products on the GPU the tokenizer and the safetensors reader done; floats, the model and GPU matmuls next

    Alongside these, a Presburger stage will decide affine goals such as aliasing and loop-carried dependence (ADR 0020). After a 0.1 release, Pia will be offered to Compiler Explorer.
