# IRGen: the scalar subset

Status: implemented in M4 ([#5](https://github.com/deanberris/pia-lang/issues/5)).

`piac --emit=mlir file.pia` lowers a program to the `pia` and `pia_contract` dialects ([ADR 0018](adr/0018-dialect-layering.md)), with control flow in upstream `scf` and functions in `func`. This page describes the subset it accepts and how each construct lowers. Anything outside the subset is reported as "not supported yet" at its source location.

## The pipeline

1. **Parse** (`src/syntax`) to the uniform syntax tree.
1. **Expand metaprograms** (`src/meta`, [meta.md](meta.md)). Binary operators become calls of core builtins, `@derive` runs, and the `let meta` items are removed.
2. **Sema** (`src/sema`) resolves written types and collects the signature of every top-level `let`, so a function can be called before its definition. It reports items outside the subset (types, modules, metaprograms) before any code is generated.
3. **IRGen** (`src/irgen`) type checks expressions as it lowers them. A separate typed AST comes when the language outgrows the scalar subset.
4. The module is run through the MLIR verifier.

## Types

| Pia | IR |
| --- | --- |
| `u8` `u16` `u32` `u64`, `i8` ... `i64` | `!pia.int<lo, hi>` with the machine range |
| `usize`, `isize` | the 64-bit ranges, printed as the aliases `!usize` and `!isize` |
| `int{lo..hi}` | `!pia.int<lo, hi>` (bounds are integer literals for now) |
| `bool` | `i1` |
| `[T; n]` | `!pia.array<n x T>` (n is a literal for now) |
| `[T]` | `!pia.slice<T>` |
| `atomic T` | `!pia.atomic<T>`, for an integer type or `bool` ([ADR 0052](adr/0052-atomics.md)) |
| `unit` | no value; a function returning unit has no results |
| `let pixel = type { r : u8; ... }` | `!pia.record<"pixel", r : !pia.int<0, 255>, ...>`, printed as `!pixel` |

Types are structural: `u64` and `usize` are the same type. `int{0..255}` is `u8`. Records are the exception: they are named, so two record types with the same fields are different types. `let byte = type u8` is another name for `u8`.

## Integers

- **Literals** take the type the context expects. With no context they are `i32`, or `i64` or `u64` if the value does not fit. A suffix (`42u8`) fixes the type. A literal that does not fit its type is an error.
- **Binary operators** arrive from expansion as calls of core builtins (`a + b` is `add a b`, [meta.md](meta.md#operators)). IRGen lowers a builtin call as the operator it stands for. They compute at the join of the operand types, the smallest range holding both. When the context expects a wider integer, they compute at that type, so `dst.[i] <- src.[i] * 3` with `u8` source and `u16` destination multiplies at `u16`. The other operand is widened with `pia.convert`. A literal takes the other operand's type, whichever side it is on.
- **Conversions**: wherever a value meets a declared type (a parameter, a return type, an annotated `let`, an assignment, an element store), IRGen inserts `pia.convert`. Widening always holds. Narrowing is a proof obligation for the verifier (M5).
- **Overflow**: `+ - * / %` lower to `pia.add`, `sub`, `mul`, `div`, `rem` with the function's overflow mode. The default is `proof`. `@overflow(wrap | saturate | trap)` on the return annotation sets another mode, `@wrap e` (and `@trap`, `@saturate`, `@proof`) sets it for one expression, and `+|` `-|` always saturate. The parser writes `@wrap e` as the prelude builtin `#overflow wrap e`, as it writes `~x` as `bnot x`. `mod` is `%`.
- **Negation** `-x` is `0 - x` at x's type, so it is an obligation for unsigned and minimum values. `-5` is a literal.
- **Comparisons** lower to `pia.cmp` at the joined type. `=` and `<>` on bools lower to `arith.cmpi`.

## Buffers

- **Indexing** `xs.[i]` is `pia.load`, and `xs.[i] <- v` on an `out` or `inout` parameter is `pia.store`.
- **Slicing** `xs.[a .. b]` is `pia.slice`, a view of the same storage. An array passed where a slice is expected becomes a `pia.slice` of all of it.
- **Array literals** `[1; 2; 3]` where an array type is expected, and top-level `let t : [T; n] = [...]`, are `pia.const_array`. A top-level constant is not a function: each use is a `pia.const_array` with the constant's name as its `label`. The elements must be integer literals for now. Passing constant data, or a slice of it, to an `out` or `inout` parameter is an error.
- **`abort ()`** is `pia.abort`, with a result of the type the context expects.

## Variants

A variant `let shape = type | Circle of u16 | Empty` is a record named `shape` with a field `tag`, `int{0..n-1}`, and one field per constructor that has a payload, named after the constructor. A constructor's tag is its position. `Circle r` is a `pia.record` with tag 0, `r` in `Circle`, and a fixed value in every other payload field. Only constructors and `match` see these fields: `.tag` and record literals are errors on a variant. Records then scalarize as usual, so the verifier and codegen need nothing new, and a variant crosses the C boundary as its fields. A payload written as a record in place, `| Rect of { w : u16; h : u16 }`, is a record type of its own, `shape_Rect`, which expansion defines just before the variant; the payload names it, and its fields keep their attributes for the variant's derives (tests/verify/record_payloads.pia). A generic variant cannot have one yet.

`match` checks its arms first: they must cover every constructor or end with a catch-all, and an arm after a catch-all, a constructor matched twice, or a catch-all after every constructor is an error. It then becomes a chain of `if`s on the tag, the last arm untested, with each arm's payload bound by a `let`. So arms carry mutable locals and join their result types exactly as `if` does.

An arm may carry contracts between its pattern and `->` ([ADR 0035](adr/0035-substitution-failure-and-total-constraints.md)): `| Some i requires i < len xs ensures result = xs.[i] -> xs.[i]`. A `requires` is not a guard. It becomes an assertion at the start of the arm, so it is proved for every value that reaches the arm, from what is known at the `match`. An `ensures` becomes an assertion on the arm's value, `result`. Handler arms are arms of a `match`, so they take contracts too, proved at each `?` that reaches them.

## Bindings and mutation

- `let x = e in body` binds an SSA value. An annotation converts `e` to the declared type.
- There is no shadowing ([ADR 0022](adr/0022-metaprogram-hygiene.md)). A `let`, parameter, loop variable or quantifier binder may not reuse the name of a local in scope, a function, a type or a core builtin. Assigning to a mutable local is not shadowing. The error suggests a primed name instead: `x'`, or `x''` if that is taken. A prime is an ordinary identifier character, so `let x' = x + 1 in ...` names a value related to `x`.
- `let x : mutable T = e in ...` makes `x` assignable. There is no memory: each `x <- v` rebinds the SSA value, and structured control flow threads it through. A mutable local assigned inside `if` becomes an extra `scf.if` result, and one assigned inside a loop becomes a loop-carried value (`iter_args` for `for`, `scf.while` operands).
- Parameters are mutable only with `mutable`. Their modifiers are kept as the `pia.modifiers` argument attribute.
- **`inout` and `out` scalars and records.** A buffer is written in place, but a scalar or a record is an SSA value, so a function hands back the final value of each `inout` or `out` parameter that is not a buffer, as extra results after its own. The caller passes a mutable variable there, and the call rebinds it, so the caller sees the write and the callee's postcondition about it. A variable passed that way inside an `if` or loop is carried like one assigned there.
- `old e` reads the parameters as they were on entry, including a mutable scalar or record parameter the body has assigned. `old` of a local declared in the body is its current value.
- **`moved`.** A local or a `moved` parameter passed as a `moved` parameter is dead after the call: using it again is an error that says where it was moved. A local moved on only one branch of an `if` or `match` is maybe moved after it, which is an error too. A borrowed parameter (the default) cannot be moved, and a local bound outside a loop cannot be moved inside it. Values of scalar types (integers, `bool`, unit) are copied, so moving one leaves the caller's copy. Assigning a mutable local gives it a value again. Contracts may still name a moved value, since they describe values rather than use them. Moving a field or an element out of a value is not checked yet.
- **`@linear`** (#56). A value of a type marked `@linear` (`let file = type { fd : i32 } @linear`), of an instance of a generic type marked so (`let box = let (t : type) (r : region) => type { ... } @linear`), or of a record, variant or instance holding one, must be consumed on every path out of its scope: passed as `moved`, or used as a value (returned, bound to another name, or put in a constructor or record). Reading a field, `len`, and passing it to a borrowed parameter only borrow it. A local that some path leaves unconsumed is an error at its `let`, and so is a `moved` parameter at the function's end. A borrowed linear parameter cannot be consumed. A `defer` that consumes the value counts on every exit. A `match` consumes its scrutinee, and `match f with | { fd } -> e` takes a record apart into its fields, which is how a linear value is finally released. A pattern that drops a linear payload or field with `_`, or leaves a linear field out, is an error. Taking a linear record apart is not yet limited to its own module.
- **Slices in records and variants.** A record field or a constructor's payload may be a slice, as in `result (borrowed(m) [u8]) OutOfMemory` or `{ data : [u8]; used : usize }`; the record is scalarized into its fields like any other, so the slice is a value of its own after that. The unused payload of a variant is `pia.empty`, a slice of length 0. An array field is not supported yet: arrays are constant data for now (an array literal's elements are integer literals, and a local array cannot be written), so a record could only hold a constant one. A buffer whose elements hold a slice is a buffer of slices, one per slice field ([ADR 0048](adr/0048-buffers-whose-elements-hold-slices.md)): reading `xs.[i].slot` and `len xs.[i].slot` works for any element type, and writing through such a slice is allowed only when the element owns it, being `@linear` or having a `drop`, as a `box` does; otherwise it is read-only. A slice taken out of an owned element is lent from the buffer while it is live. An element's slice may be reached through a record's field, as `v.buf.[i].slot.[0] <- x` writes through the `i`th box of a vector's buffer when `v` is `inout`. Codegen lowers each to a buffer of addresses and one of lengths ([codegen.md](codegen.md#types); tests/verify/slice_buffers.pia, tests/verify/vec_boxes.pia, tests/irgen/slice_buffer_errors.pia, tests/codegen/vec_boxes_core.pia). An owning element read as a value moves out of its buffer: IRGen stores it back with every slice empty, a store marked `pia.moved_out`, which codegen keeps so that the element's length is 0 at run time too, and drops that store again when the read turns out to be a borrow, as in `xs.[i].slot` (ADR 0048, section 6). Moving one out of a buffer the function cannot write is an error (tests/irgen/move_out_errors.pia). A store of a whole owning element is marked `pia.fills`, and the verifier proves the element written over owns nothing; a function whose lent buffer is `out` is marked `pia.out_result`. A slice that an `if` or `match` chooses is read from the branch taken, but the verifier refuses a write through it, since it does not know which buffer the write reaches.
- **Writable loans.** A local holding a borrowed buffer whose result type says `out`, `inout` or `mutable`, as `alloc`'s `borrowed(m) out mutable [u8]` does, may be written, like an `out` parameter. A lender may be passed `inout` while it is lent, as `alloc` updates its allocator: the callee's contract is what keeps the earlier loans valid. Passing it `out` makes it anew, so that is an error while it is lent. The verifier sees a borrowed buffer result as fresh memory, which `alloc`'s loans are; for a result that views its lender, as `xs.[a .. b]` returned through `borrowed(xs)`, a write through it does not yet reach the lender's elements.
- **Fields as `inout` arguments.** An `out` or `inout` argument may be a field of a mutable variable, at any depth, as `take_slot g.small` takes from one pool of a record of pools (tests/verify/size_classes.pia). After the call the variable holds a copy of itself with that field replaced, so the rest of the record is unchanged. The variable must not be lent at the call, as for `g.f <- v`.
- **Borrows into `inout` parameters.** `(v : borrowed(m) inout mutable vec)` says that the new value of `v` may hold a loan from the parameter `m`, as `push m v x` may store a buffer from the allocator `m` in the vector `v`. After the call, the caller's variable borrows from the argument passed as `m`, so it cannot outlive it. A function that stores a value borrowed from another parameter in an `inout` or `out` parameter without saying so is an error.
- **Borrows** (#70, ADR 0026). A function whose result type says `borrowed(m)` returns a value borrowed from its parameter `m`, as an allocator's `alloc` does. The argument passed as `m` must be a named value, or something already borrowed from one, and the call's result is then borrowed from it. A local holding such a value borrows from it too, and so does anything taken from that local: a field that is not copied, a slice, a `match` or `?` payload, a record or constructor holding it, or either branch of an `if`. Only the parts of a value whose types some borrowed result borrows count, so an integer field of a borrow, a length, or the error of `result (borrowed(m) [u8]) e` borrows nothing. A borrow lasts until the last use of the local that holds it ([ADR 0042](adr/0042-lifetimes-liveness-and-escape-analysis.md)), not to the end of its scope. Until then the lender cannot be moved or consumed, passed as `out`, `inout` or `mutable`, or assigned; each is an error that names the borrower and where it is used next. A use is a later mention of the local in its scope, in evaluation order, which follows the source; a mention in a cleanup, such as a `defer` or a drop, counts as later, since it runs at the exit; and inside a loop that began after the local was bound, the borrow lasts through the loop (tests/irgen/borrow_liveness.pia). A `let`'s value cannot be borrowed from its own local, since it would outlive it, and a function's result can be borrowed only from the parameter its result type names. Borrows of slices of local arrays are not checked yet.
- **Region parameters** ([ADR 0042](adr/0042-lifetimes-liveness-and-escape-analysis.md), step 2). A borrow can name a region instead of a value: `(r : region)` is a parameter of a generic type or a function, and `borrowed(r)` on a record field, a result or an `inout` parameter says the value borrows from `r`. So `let vec = let (t : type) (r : region) => type { alloc : bump t r; buf : borrowed(r) mutable [t]; len : usize }` holds both an allocator and the buffer it lent, and neither borrows from the other or from the vector (tests/verify/vec_region.pia). Regions are erased before anything else (irgen/Regions.cpp): `vec u16 r` and `vec u16` are one type, and a type application may leave its regions out. Each region argument must name a region parameter in scope, and a function's `borrowed(r)` needs a parameter whose type mentions `r`. In a function, a parameter whose type mentions `r` holds loans from `r`, which is outside the function: they may go into another parameter whose type mentions `r`, or out through a result that mentions it, and nowhere else. A parameter of a type with region fields that names no region has a region of its own, so its loans stay in it. At a call, a result or `inout` parameter that mentions `r` borrows what the arguments for `r`'s parameters borrow, not those arguments themselves: `alloc v.alloc n` does not lend `v` to the buffer `push` stores in it. A field read of a region field borrows what its record borrows, so the memory a region lends lasts as long as whatever lent it, such as a `with_arena`, and an allocator that frees blocks one by one must hand them out as owned or linear values instead (tests/irgen/region_errors.pia, region_sig_errors.pia). A concept may take regions too, `let meta Allocator (a : type) (t : type) (r : region) : concept`: a requirement's parameter whose type mentions one of the concept's type parameters is in its regions, and a requirement's result may say `borrowed(r)`, so generic code over an allocator stores what it allocates (tests/verify/vec_allocator.pia). A type parameter such a constraint names, as `a` in `(a : type where Allocator a t r)`, is in the constraint's regions, so a parameter `(m : inout mutable a)` holds loans from `r` and a result that mentions `r` may return what `m` allocates (lib/Pia/Mem/Box.pia's `make`, tests/irgen/region_concept_errors.pia). An interface (ADR 0039) may list a generic type with regions and a function with region parameters; they are erased there as in the module, and an importer checks its own uses against the regions the interface names (tests/modules/regions.pia, region_import_errors.pia). Regions of variants and regions of a lambda are not supported yet.
- **Scoped regions** (#70, ADR 0026). `with_arena 256 (let (a) => body)` is a `let` of `a : mutable arena`, where `arena` is `type { mem : [u8]; used : usize }` (a program may define its own `arena` with these fields). `a.mem` views 256 fresh bytes (`pia.region`), every one zero, and `used` starts at 0, so a bump allocator over the arena is ordinary Pia, and `a.mem.[i] <- x` writes it (a field of a writable record can be written in place), as in tests/verify/arena.pia. The arena is borrowed from itself, so the `with_arena`'s value can hold neither the arena, nor a view of its memory, nor anything allocated in it, and the arena cannot be moved; each is an error at the `with_arena`'s body. The size is an integer literal of at most 1 MiB, since the region lives on the stack: codegen makes it once on entry to the function and zeroes it each time the `with_arena` is entered, so one in a loop does not grow the stack. Larger regions wait for pages over mmap.
- `xs.[i]` lowers to `pia.load` and `xs.[i] <- v` to `pia.store`. Writing requires the parameter to be `out` or `inout`. Indices go through `pia.to_index`. `len xs` is `pia.len` followed by `pia.from_index` to `usize`.

## Control flow

- `if c then a else b` lowers to `scf.if` with the joined result type. An `if` without `else` must have type unit.
- `&&`, `||` and `==>` in code short-circuit, so they lower to `scf.if`. This keeps `i < len xs && xs.[i] <> x` from loading out of bounds.
- `for i in lo..hi step s do ... done` lowers to `scf.for` over `index`. The bounds are joined to one type, and `i` is bound with `pia.from_index` at that type. The range is half-open. Two literal bounds are `usize`.
- `while c do ... done` lowers to `scf.while`. The condition is computed in the `before` region.
- `a; b` evaluates `a` for its effects. `a` may not be a `result`: a result is never dropped unexamined, and neither is a loop body's value.

## Errors

`result t e` (`Ok` of a `t`, or `Err` of an `e`) is in the prelude, unless the program defines its own `result`, `Ok` or `Err`. `e?` and `handle` follow [ADR 0028](adr/0028-error-propagation-and-cleanup.md):

- A `?` ends its scope early, so it must be in a *tail* of the scope: the scope itself, the body of a `let ... in`, the second part of `a; b`, a branch of an `if` or an arm of a `match` that is itself a tail, or anything those always evaluate first (a `let` value, an `if` condition, an operand). A `?` inside a branch whose value the scope still needs, or in a loop body without a `handle` of its own, is an error.
- There it becomes an `if` on the result's tag. `Ok` goes on with the rest of the scope, with the payload where the `?` was. `Err` becomes the scope's value: `Err e` returned to the caller when no `handle` encloses it, which needs the function to return a `result` with the same error type, or the handler's arms for that error.
- The arms are generated at each `?` that reaches them, so each is checked and proved once per `?`, knowing only what holds there: what was bound before it and what earlier calls promised. An arm that uses a name bound after some `?` that reaches it is an error that names that `?`.
- At each `?` the arms taken are those for the error type's constructors, in order, up to the first catch-all. A constructor no arm takes is an error at the `?`, and an arm no `?` reaches is an error at the arm, as is a `handle` with no `?` in its scope.
- `| C p ->` binds the payload, `| e ->` the whole error, and `| C as e ->` both tests `C` and binds the whole error.
- An error set `a | b` is one variant holding the constructors of each member, ordered by the members' names, so `b | a` is the same type. A value of a member converts to the set: its tag moves to its block of the set's constructors. So a `?` whose errors are a member of the function's error set passes them on, `Err NoEntry` builds the set directly, and a handler matches the set's constructors. Two members may not share a constructor name. A set does not yet convert to a larger set.
- An expression is evaluated from its first `?` on: in `g a + f x?`, `f x` runs before `g a`. A `?` inside a handler arm is not supported yet.
- `defer d; rest` registers `d` as cleanup for `rest`, the rest of its sequence (#85). Each normal exit from `rest`, a node whose value is `rest`'s value (the body of a `let`, both branches of an `if`, each arm of a `match`), gets a copy of `d` after its value, and each `?` that leaves the scope runs the scope's `defer`s, innermost first, before its error goes to the handler or the caller. So cleanup runs in reverse order of registration on every exit, and the verifier proves it like any code at that exit. `d` must have type unit and contain no `?`. The error in flight is the `?`'s own payload, an immutable value read after the cleanup, so no cleanup can change or replace it. `defer?` is not supported yet.
- **`drop`** (#85). A type has a drop when a non-generic `drop (x : moved t) : unit` is in scope, which is how it meets the `Drop` concept (ADR 0034). A local or `moved` parameter of such a type is dropped at every exit from its scope that has not consumed it, as if by a `defer` registered where it is bound: after its scope's value on a normal exit, and before the error on a `?`. Using it as a value or passing it as `moved` consumes it, so a returned value is not dropped. An exit where it is consumed on only some paths is an error, since there is no runtime flag to decide. `drop` itself does not drop its argument again; it takes it apart with a record `match`. `@derive(drop)` is not supported yet.

## Contracts

| Pia | IR |
| --- | --- |
| `requires p` | `pia_contract.requires` at function entry |
| `ensures p` | `pia_contract.ensures` before the return, with `result` bound to the return value |
| `decreases m` on a function | `pia_contract.decreases` at entry |
| `invariant p`, `decreases m` on a loop | at the head of each iteration: the start of the `for` body, or the `before` region of `scf.while` |
| `assert p`, `assume p` | `pia_contract.assert`, `pia_contract.assume` |
| `old e` | `pia_contract.old` |
| `forall (i in lo..hi). p` | `pia_contract.forall` whose block argument is `i`, yielding `(lo <= i && i < hi) ==> p` |
| `exists (i in lo..hi). p` | `pia_contract.exists`, yielding `lo <= i && i < hi && p` |
| `forall (k : u8). p` | quantifies over the whole type, with no guard |

Several binders nest one quantifier op per name, so a later range can mention an earlier name. Inside contracts, which have no effects, `&&`, `||` and `==>` are plain `arith` logic, and `==>` is `(a xor true) or b`. Whether arithmetic in contracts is exact or follows the overflow mode is settled with the verifier in M5. Quantifiers are rejected outside contracts and assertions.

## Records

A `let name = type { field : T; ... }` item defines a record type. Records are values, like integers.

- **Literals.** `{ r = v; g = 0; b = 0; a = 255 }` lowers to `pia.record`, with the fields in declaration order, whatever order they are written in. Its type comes from the context. Failing that, it is the one record type whose fields are exactly these. Every field must be given, once.
- **Field reads.** `p.r` lowers to `pia.field %p, "r"`.
- **Field assignment.** `q.r <- v` on a mutable local record rebuilds `q` with one field replaced. So, like any mutable local, `q` is an SSA value threaded through `scf.if` and loops.
- **Equality.** `p = q` on records calls `eq_<name>`, which `@derive(eq)` makes ([meta.md](meta.md#derives)). `<>` negates it. In a contract, a record or variant without an `eq_` compares as a value: field by field, and a variant by its tag and then the payload it holds. Two arrays or slices compare by length and then element by element, as a `forall`. So a generic contract such as `ensures result = v`, which the definition check accepts for every type, means the same in every instance.
- **Buffers of records.** `[pixel; 8]` and `[pixel]` hold records. `xs.[i]` reads one, `xs.[i] <- p` writes one, and `xs.[i].a <- v` reads element `i`, replaces its field and writes it back. Writing needs an `out` or `inout` parameter, as for any buffer.
- **Not yet supported:** buffers inside records, and attributes on type items other than `@derive`.

The verifier and code generation do not see records. `transforms::scalarizeRecords` replaces each record value with its fields first, using MLIR's 1:N dialect conversion. A `pixel` parameter becomes four parameters named `p.r`, `p.g`, `p.b` and `p.a`, a `pixel` result becomes four results, and `pia.record` and `pia.field` disappear. `old p` becomes `old` of each field. A buffer of records becomes one buffer per field, struct of arrays: an `xs : [pixel]` parameter becomes `xs.r`, `xs.g`, `xs.b` and `xs.a`, and loads, stores, views and `len` apply to each. The field buffers of a slice share one length, so every one after the first carries `{pia.length_of = k}`, naming the argument whose length it has; the verifier gives them that length, and the C entry point takes it once. A store of a field read back from the same element is dropped, so `xs.[i].a <- v` writes only `xs.a`. The field copies of one load, store or view share its index and length, so every copy after the first carries the unit attribute `pia.bounds_shared`: the first carries the bounds goal, and the verifier only assumes it for the others, so each index is reported once. Copies of a load or view that nothing uses are erased, and the first copy still in use carries the goal, so a record read only by a contract raises no goal, as a scalar one would not.

## Functions

Each top-level `let f (x : T) ... : R = body` becomes `func.func @f`. Parameters need annotations. A `let` with no parameters becomes a function with no arguments, and its uses call it. The return type may be left out, and then it comes from the body. Such a function cannot be called before its definition, or recursively. Calls must pass every argument, since partial application and functions as values come later.

A generic function, one with `(t : type)` parameters, is never generated itself. Each call works out the type arguments: first from `f<u8>` or `f<t = u8>`, then by matching the written types of the parameters that mention an unknown type parameter against the types of their arguments, which are generated first for this, then from the type the call is expected to have. The call goes to the instance, a private `func.func @"f<u8>"`, which is made on first use and generated after the function that used it, with each type parameter naming its argument. Generic types work the same way: `option u8` is a record type named `option<u8>`, made the first time it is used, and a generic constructor such as `Some` builds the instance it is expected to build, or else the one its payload's type gives.

A constraint on a type parameter, `(t : type where Ord t)`, names a concept: a `let meta C (t : type) : concept = sig ... end` that the metaprogram pass keeps in the program. Each call checks that the deduced type arguments meet it (the use check of ADR 0034). A requirement `let f : (a : t) -> bool` is met by a function in scope with that name, those parameter types and modifiers, and that result, and `include` requires another concept. A generic function meets it too, at the type arguments its parameters and result deduce, when those meet its own constraints: `alloc` over `bump t r` meets Allocator's `alloc` for `bump u16` at t = u16, and that instance is made and proved like any other (tests/verify/generic_meets_concept.pia, tests/modules/generic_meets.pia). A function that is not generic is tried first. A generic that would meet a concept only through its own constraint, such as `let same (t : type where Same t) ...` for `Same`, does not. Whether a concept is met is decided once per concept and type arguments. Each law, `let lemma name params ensures p`, becomes a lemma for those type arguments, `@"Ord<u8>.irreflexive"`, generated and proved like any other function. A requirement's contract becomes one too, `@"Ord<u8>.less.contract"`: under the requirement's `requires` it asserts the function's own `requires`, and it ensures the requirement's `ensures` of a call of the function. In an overload set, a generic whose type arguments do not meet its constraints is removed from the call, and the error for a call with no candidate left gives that reason.

A generic body is checked once, at its definition (the definition check). It is generated with each type parameter standing for an unknown type, a record named after the parameter with no fields, and then thrown away with every instance it made. A call with an argument of such a type resolves against the requirements of the concepts its constraints promise, including the ones they include, and a generic it calls must have constraints those concepts promise. Anything else, such as `<` on a `t` or a function the constraints do not require, is an error there, with a hint naming a concept that requires the function. A contract may still compare such values with `=`. Each instance then resolves its calls by its concrete types, which picks the function that met the concept at the use check, since two functions cannot share a name and parameter types.

An adapter, `let adapter by_red : Same pixel = struct ... end`, holds functions named after it, `@"by_red.same"`, which no call reaches by name. The use check meets a concept directly when it can. Otherwise it uses the adapter the call names (`alike<Same = by_red>`), the one the function being generated already chose, or the only adapter in scope for that concept and those types. Two such adapters, with neither named, are an error. An instance made through adapters is named after them, `@"alike<pixel, Same = by_red>"`, and while it is generated a call by a requirement's name goes to the adapter's function in place of any with the same parameter types. The concept's laws and requirement contracts are proved the same way, about the adapter's functions.

A type-level metaprogram, a `let meta` whose parameters are all types and that returns a `type` or a `bool`, also stays in the program (ADR 0035). A type such as `widen u8` or `widen t` runs it on the types it is applied to, and gives the type it returns. A `where` may state a predicate over types beside its concepts: a comparison, `||`, `==>`, `<==>`, or a call of such a metaprogram that returns a bool, as in `where Ord t && size_of t <= 8`, or `where t = u8 || t = i8`. Each call evaluates it for the deduced type arguments; when it is false, the candidate is removed with the reason "the constraint 'small t' is false for t = u32". A concept can only be joined to the rest by `&&`. Types are the metaprogram's values: a type's name denotes it, `=` compares types, `name t` spells one, and `size_of t` gives the bytes it takes (an integer the smallest of 1, 2, 4 or 8 that holds its range, a bool 1, an array its elements', and a record the sum of its fields'; a slice has no fixed size). Such a metaprogram must terminate: recursion only on components of a type parameter, no mutual recursion, and nothing that reads or changes the program ([meta.md](meta.md#type-level-metaprograms)); a use of one that may not is an error at the use. When a candidate's signature cannot be formed for the deduced types, because a metaprogram in one of its types or predicates fails, the candidate is removed with that reason, and the call falls back to the others (substitution failure, ADR 0035). Only the signature fails softly, never a body, and a metaprogram in a type outside a candidate's signature still fails with an error. `piac --explain-overloads=file:line` prints, as notes, each call on that line: its candidates, why each removed one was, and which one it chose. In the definition check, a type-level metaprogram applied to a type parameter stands for an unknown type too, and a signature with one has its body checked in each instance instead, since its types are only known there. A generic body may call a generic with a predicate only if its own constraints state the same predicate, and a generic whose constraints state every predicate of another's, and more, is the more specific. A type-level metaprogram applied in a parameter's type does not deduce its type arguments.

A name may have several generic overloads. The first keeps the name and the others are numbered, `rank#2`, and so are their instances, `@"rank#2<u8>"`. When two generics both fit a call equally well by their arguments, the more specific one wins. A is more specific than B when A's parameter types, with stand-in types for its type parameters, are an instance of B's but not the reverse. When each is an instance of the other, A is more specific when its constraints entail B's and not the reverse. A concept is entailed when A's constraints promise it through `include`, or when the requirements they promise include every one of its requirements and it states no law or requirement contract. Laws and contracts would need a proof, which is not done yet. Two generics with the same patterns whose constraints entail each other are an error at the second definition. A call with no single most specific candidate is an ambiguity error that lists them. Overloads with the same parameter types are told apart by their preconditions. They must be ordered: each one's `requires` clauses, compared with the parameters renamed by position, include every clause of the next, which proves that each precondition implies the next. They must also return the same type. They are named `copy(out [u8], [u8])#2` and on. A call that only they fit goes to the least specific, with all of them, most specific first, in `pia.overload_candidates`, and the verifier picks the most specific one whose precondition it proves at the call ([the verifier](verifier.md#choosing-overloads-by-precondition)). A call inside a contract uses the least specific, so a contract means the same in every build.

A higher-order function, one with a parameter of function type such as `(p : u8 -> bool)`, is never generated itself either (ADR 0044, step 1). Sema records its function parameters. Each call that passes a lambda or the name of a top-level function for them goes to a specialisation, `@"find[lambda@f.pia:12:9]"`, made on first use and cached by the function and its arguments: a copy of the function without those parameters, in which each one's name is the argument's symbol. The copy keeps the type parameters, so a generic one is then called through the generic path with the other arguments. A lambda becomes a private function `@"lambda@f.pia:12:9"` with its parameters, its result type if written (else the arrow's, else the body's), the arrow's `requires` renamed to its parameter names, its own `requires` asserted at the start of its body, and its own `ensures` and the arrow's. A named function is called directly when the arrow has no contract; otherwise through a wrapper, `@"succ@f.pia:20:9"`, that has the arrow's contract. `let sq = let (x : i32) : i32 => x * x in sq 3` binds `sq` to a lambda's function. A lambda anywhere else is an error naming ADR 0044.

Step 2 adds function objects and overloading (ADR 0044, section 4). A call `g x` where `g` is a local of a record or variant type is `apply g x`. A local passed for a function parameter must have such a type, with one `apply` whose first parameter is that type and which takes as many arguments after it as the arrow; the specialisation, `@"find[below]"`, keeps the parameter, with the object's type, and calls `apply` (or, when the arrow has a contract, a wrapper `@"apply@f.pia:30:11"` with it) at each application. The prelude concept `Function f a r`, with the one requirement `apply : (g : f) -> (x : a) -> r`, is defined for a program that names it and defines no `Function` of its own, so a generic can take `(f : type where Function f t bool) (p : f)` and is proved once. Higher-order functions may share a name with each other and with ordinary overloads; they are named after their line, `find#line12`. At a call, a higher-order candidate is removed when an argument for a function parameter is not a lambda, a named function or a function object, or an argument for a value parameter is a lambda or a named function, and an ordinary one when any argument is a lambda or a named function, or the type of a named argument clashes with its parameter. One candidate must be left; `--explain-overloads` lists why each was removed.

Step 3 adds captures (ADR 0044, section 6). A lambda lists them after `let`: `[lo, borrowed keys, inout n]`, a bare name copied, `borrowed` a shared loan and `inout` an exclusive one. Every local the body uses must be listed, once, and every listed name used; a copy must be of a copyable value, and an `inout` capture of a `mutable` variable; only an `inout` capture may be assigned; capturing a linear or `drop` value comes with step 7. A lambda that captures has its own record type, `lambda@f.pia:12:9`, with one field per capture, and its function is an `apply`, `@"apply[lambda@f.pia:12:9]"`, whose first parameter is the record and whose body reads each capture as a field of it. As a value, anywhere, a lambda is that record, made by a record literal of its captures, so a `let` of it is a function object and `where Function f t bool` deduces `f` to it. Passed for a function parameter, it is a function object of that type, so the specialisation takes the captures in one argument. A borrowed or referenced capture is a loan the closure holds until its last use (ADR 0042): a borrowed variable cannot be assigned, nor a borrowed buffer's elements, and a referenced one cannot even be read. With an `inout` capture, `apply` takes the closure `inout mutable`, so each call threads it back; a `let` of such a closure is mutable, the variables it references are rebound to its fields after each call, and loops carry both. Passed for a function parameter written `(f : inout t -> unit)`, it is made in a hidden mutable local and the specialisation takes it `inout`; an arrow without `inout` refuses it, and such an `apply` cannot be called in a contract. A lambda that captures nothing is still called directly.

Step 4 adds untyped and generic lambdas (ADR 0044, section 2). At a call of a generic higher-order function, its type parameters are first deduced from the arguments that fix them without being generated: named values, and the written types of typed lambdas, function objects and named functions. An untyped lambda parameter then gets the type of the arrow's domain under those bindings, written in the lifted function as a type alias, `type#lambda@f.pia:12:9#x`, and the deduced bindings join the specialisation's generic call. A lambda's result type, when it is not written and the arrow's cannot be resolved, is inferred by generating its body once in a function that is thrown away; its errors are dropped there, since they come again when it is generated for real. A `let` of a lambda that captures nothing and has untyped parameters is a generic function, `lambda@f.pia:12:9`, with an implicit type parameter `x#type` per untyped parameter; explicit `(t : type where C t)` parameters are kept, and when one has a constraint the lambda's definition is checked and proved once (ADR 0043), queued like an instance.

Step 6 proves each higher-order function once (ADR 0044, section 5; ADR 0043). Before any call, each pure function parameter `p` of `f` becomes a type parameter `p#type` constrained by a concept made for it, `f#p`, whose one requirement is `apply` with the arrow's types and its `ensures`; `p` gets that type, so `p x` is `apply p x`. The copy, `f#proof`, is checked like a written generic, and its generic proof is kept when it is parametric. Each specialisation of `f` is then marked as an instance of `f#proof`, and the verifier discharges it when its calls match the proof's, a call of `apply` matched by the argument's function, which must return: the argument's own check against the arrow's contract happens where it is passed (its lifted function's `requires` and `ensures` are the arrow's). A law applied to `p` in a contract, such as `requires Pia.Fn.strict_weak_order p`, is part of the copy, and so is an arrow's `requires`: in a definition check, each call of a requirement with a precondition asserts it with the call's arguments, and the requirement's axiom is guarded by it. An arrow with `inout`, a specialisation whose closure writes a capture, and a function whose copy is not parametric are proved at each specialisation, as before. Spec functions are left alone.

Step 7 adds partial application, functions as results and moved captures. A call of a lone top-level function with arguments left, `below lim`, is the lambda `let [lim] (arg#1 : u8) : bool => below lim arg#1`: a local argument is captured (copied, or borrowed when it cannot be), a literal is written in, and any other argument must be bound first. A function whose result is written as a function type, `: u8 -> u8`, has the type of the closure its body makes, found by generating the body once before its first call; callers apply it like any function object. A capture list may say `[moved t]`: the closure owns `t`, which the record literal that makes it consumes, and when a moved capture has a `drop` the closure gets one, `@"drop[lambda@f.pia:12:9]"`, that takes it apart so each field is dropped once. A lambda in one place may be made with different captures in different copies of its body, such as a proof and a specialisation, and each copy gets its own closure type, `lambda@f.pia:12:9#2`.

## Atomics

An atomic cell, `atomic t`, is a place, not a value ([ADR 0052](adr/0052-atomics.md)). Its type is `!pia.atomic<T>` for an integer type or `bool`. A range type such as `atomic int{0..64}` is a refined cell: its range is an invariant of the cell across every task. The ops are core builtins with the order first:

| Pia | IR |
| --- | --- |
| `atomic_new v` | `pia.atomic.new`, the cell's type from the context or from `v` |
| `atomic_load o c` | `pia.atomic.load o` |
| `atomic_store o c v` | `pia.atomic.store o` |
| `atomic_swap`, `atomic_add`, `atomic_sub`, `atomic_and`, `atomic_or`, `atomic_xor`, `atomic_min`, `atomic_max` | `pia.atomic.rmw <kind> o`, with `overflow(m)` on an add or sub |
| `atomic_cas ok fail c expected desired` | `pia.atomic.cas ok fail` |
| `fence o` | `pia.fence o` |

- **Orders** are the names `relaxed`, `acquire`, `release`, `acq_rel` and `seq_cst`, read from the order position only. So an order is always a compile-time constant, and the names stay free for functions such as `release`. Each op takes the orders in ADR 0052's table, and a failure order of `atomic_cas` is `relaxed`, `acquire` or `seq_cst` and no stronger than the success order. Anything else is an error that lists the orders the op takes.
- **Values** stored or combined are converted to the cell's type, so storing into a refined cell is a range goal. On a refined cell `atomic_and`, `atomic_or` and `atomic_xor` are errors, since their results cannot be proved to stay in range.
- **Overflow.** `atomic_add` and `atomic_sub` take only a mode written on the expression itself, `@wrap (atomic_add o c v)`, and are an error without one, even inside an `@overflow(...)` function. A plain cell takes `wrap`, `trap` or `saturate`. A refined cell takes only `proof`, and IRGen adds `pia.add` (or `sub`) of the old value and `v` in proof mode, whose goal is that the result stays in the range. Nothing reads its result, and codegen drops it.
- **Ownership.** A cell is not copyable. Naming it in an op, or passing it to a borrowed parameter, borrows it; any other use as a value moves it, so it cannot be used afterwards. A cell local cannot be `mutable`. The ops are not allowed in contracts or ghost code.
- **Not yet:** a cell in a record field, a buffer of cells, a function returning a cell, and a lambda capturing one. Each is an error that says so.

## Not yet

Local functions, captures, untyped lambdas and other function values, recursive types, `dyn`, floats, `spread` and tiles (M8), type-level lengths (`[T; n]`), refinements (`where` on values), modules, `decreases` for metaprograms, generic adapters, entailment proved from laws and contracts, and precondition orders that need a proof rather than included clauses.
